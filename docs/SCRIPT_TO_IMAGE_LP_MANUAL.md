# 台本から再現する「完成画像型」LP 制作マニュアル

## 目的と適用範囲

このマニュアルは、確定台本を受け取り、本文を**画像生成AIで作った完成画像**として見せる記事LPを再現するための作業手順です。

このクボタ筑波LPでは、本文の見出し・本文・数字・表・図解・注意書き・イラストを、セクション単位の完成画像に含めます。一方で、CTA、計測、ページの外枠、フッター、ページ遷移はWeb実装で扱います。

最優先は「短くすること」ではなく、台本中の応募判断に必要な情報を残しながら、**重複を減らして理解しやすい密度に再編集すること**です。

## 1. 作業を始める前に確定すること

台本を受け取ったら、いきなり画像を生成しません。次の3つを先に作ります。

1. **事実・条件台帳**
   - 金額、期間、支給条件、勤務地、勤務時間、例外、注意書きを台本どおりに抜き出す。
   - 数字は出典・条件・表示箇所をセットで管理する。
   - 台本にない数字、断定、比較、体験談は追加しない。
2. **情報設計表**
   - 各セクションを「結論 → 根拠 → 補足」で完結させる。
   - 同じ数字・同じ注意書きは原則1か所に集約する。別の箇所で再掲する場合は、結論に必要な最小限にする。
   - 台本に含まれる応募判断材料（給料、手当、寮、仕事、大変さ、未経験の根拠、勤務、体験例、比較、適性、正社員制度、応募前確認、FAQなど）を、削除ではなく関連ごとにまとめる。
3. **ページ別の訴求表**
   - 検索意図ごとに、FV・最初の答え・本文順・最初のCTA・後半CTAを定義する。
   - 本文素材を共通化しても、検索語に対する最初の答えを同じにしない。

台本に混在する「制作指示」と「読者向け本文」は区別します。制作指示は実装・生成の要件として扱い、読者に見せる事実は台本と根拠資料にあるものだけを使います。

## 2. 情報設計の基本

### 1画面（1セクション）の役割

1つの画像で、読者が次の順に読める状態にします。

1. 何が結論か
2. なぜそう言えるか
3. どの条件・例外を見ればよいか

「日給」「月収」「手当」「年間合計」「貯金」のような関連数字を、説明のたびに新しい画像に分割しません。主張の目的が同じなら、表・式・短い注記を使って同じセクションにまとめます。

### 全体のリズム

- 大きな話題は目安として7〜9章に整理する。ただし、実際の画像枚数は内容の読ませ方に応じて増減してよい。
- 仕事、勤務・生活、寮・立地、収入・貯金、応募判断のように話題が変わる地点だけ、Web側で控えめな余白・淡色面・短いルールなどを使い、自然な章の切り替わりを作る。
- すべての画像の間に同じ線や大きな余白を入れない。CTA自体が区切りになる場所には、追加の装飾を重ねない。
- 画像が縦に並んでいるだけに見えないようにする。ただし、既存画像を作り直さずに済む問題は、まずWeb側の余白・背景・配置で解決する。

## 3. 画像生成AIで作る範囲

### 必須ルール

- 本文セクションは、**文字・数字・表・図解・注意書き・装飾・イラストを含む完成画像**として生成する。
- 本文の再構成をHTML/CSSで行わない。HTML/CSSで作ってよいのは、CTA、外枠、フッター、計測、画像配置、最小限のセクション境界のみ。
- 画像内の文章・数字は、確定した事実・条件台帳から転記する。生成結果の文字化け、誤字、数字違い、条件漏れを必ず目視で修正・再生成する。
- 新しい事実、根拠のない便利さ・近さ・働きやすさ、全員に当てはまるような断定は入れない。

### 画像プロンプトに必ず含める指定

1. セクションの目的と、読者が読み終えたときの結論
2. 台本から使ってよい全文、数字、注記
3. 既存LPのデザインDNA
   - 白ベース、青緑の見出し、オレンジの重要数字、薄水色の補助面、薄黄色の注意エリア
   - 親しみやすい同一キャラクター、同系統の線画アイコン、既存の線の太さと余白感
4. 画面内の情報優先順位（見出し、主数字、根拠、補足、注意書き）
5. 既存画像と横幅・トーンを合わせること
6. 「文字・図解まで含めた1枚の完成画像。HTML部品・枠付きモックアップ・コラージュにしない」こと

### 画像の自然さ

- 縦横比を維持する。横引き伸ばし、縦圧縮、人物・建物・部屋・財布・工場設備・アイコンの変形は禁止。
- 枠に合わない場合は、トリミング、余白、画像の高さ、レイアウト、またはその枠専用の再生成で対応する。
- 既存の人物を使う場合は、顔・制服・線の太さ・色味を揃える。キャラクターだけ別の絵柄にしない。
- セクション末端は、隣接画像とつながる白または淡色で自然に終える。不要な外枠、影、二重罫線、画像の重ね合わせが分かるつなぎ目を入れない。
- 画像は意味のある内容に使う。観光案内、素材集、飾りだけのカード増殖にしない。

### ファイルの置き方

- 公開画像は `public/lp-images-v5/` に置く。
- 同じ画像を上書きせず、意味が変わる改訂は `15_location_holiday-v2.webp` のように用途と版をファイル名に入れる。
- 実装側で必ず実寸の `width` と `height`、内容が分かる `alt` を指定する。
- WebPを基本とし、画像生成後に横幅・縦横比・文字の可読性を確認する。

## 4. 3Clusterの実装ルール

対象ページは、同じ共通本文素材を使いながら、検索意図に応じて最初に見せる答えと読む順番を変えます。

| Cluster ID | URL | 主な検索意図 | 最初に答えること |
| --- | --- | --- | --- |
| `FACTORY_UNEXP` | `/factory-unexp/` | 工場未経験で働けるか | 未経験でも検討できる根拠、仕事と大変さ |
| `PERIOD_INCOME` | `/period-income/` | 1年でいくら残せるか | 年間収入・貯金のモデルケースと条件 |
| `PERIOD_JOBDESC` | `/period-jobdesc/` | 期間工の仕事内容は何か | 5工程と工程ごとの大変さ |

### 変更する場所

- ページ固有のFV、title、description、CTA文言は `src/data/kubota-lp3/content.ts` の `clusters` で管理する。
- 各ページの本文画像の順番、CTA挿入位置、章区切りは `src/components/kubota-lp3/KubotaLP.astro` の `itemsByCluster` で管理する。
- 共通本文画像のファイル・実寸・altは同コンポーネントの `bodyImages` で管理する。
- 3ページの内容を一律に変えない。画像を追加・差し替えたら、3Clusterそれぞれで「FV → 最初の答え → 本文順 → CTA」が検索意図に合うか確認する。

### CTAの扱い

- CTAはHTML/CSSで実装する。本文画像内に応募用ボタンを焼き込んで実リンクの代わりにしない。
- CTAは、理解が進んだ直後（最初の答えの後、収入・貯金の後、適性確認の後、最終確認の後）に置く。
- 文言は前後の内容と一致させる。例：未経験の説明後に「未経験で働ける条件を見る」、収入説明後に「現在の募集条件を見る」。
- `AFFILIATE_URL` は `src/data/kubota-lp3/content.ts` に集約し、CTAには `target="_blank"` と `rel="sponsored nofollow noopener"` を維持する。
- クリック計測は `data-affiliate`、`data-location`、`cta_click` を維持する。CTAを増やしたら、位置名も重複なく追加する。
- 動きは押下感が分かる程度に留める。常時跳ねる・発光し続ける・枠と矢印の寸法が合わないアニメーションは使わない。`prefers-reduced-motion` も維持する。

## 5. 実装時の注意

### 画像の表示

```astro
<img
  src="/lp-images-v5/example.webp"
  alt="画像が伝える内容"
  width={実寸の幅}
  height={実寸の高さ}
  loading="lazy"
  decoding="async"
/>
```

- `display: block; width: 100%; height: auto; border: 0;` を守り、画像の縦横比を変えない。
- 画像そのものに枠線を付けない。
- 微小な画像の継ぎ目が出る場合は、まず画像の端の色を確認する。必要な場合だけ、隣接セクションの `-1px` 重なりなど最小限のWeb側調整を使う。
- 章の切り替えは、話題が切り替わる箇所だけに `chapterBreak` を付ける。すべての画像に付けない。

### 変更してはいけないこと

- 台本の事実・数字・条件・注意書きを、デザイン都合で削除・改変しない。
- ユーザー承認前に、公開画像や本文を勝手に差し替えない。
- `public/CNAME`、`.github/workflows/`、計測ID、アフィリエイトURLを、依頼がない限り変更しない。
- 完成画像型LPを、読みやすさの名目でHTMLカードLPへ置き換えない。

## 6. 画面確認（必須）

生成画像を置いただけでは完了ではありません。ローカルでページ全体を読み、最低でも以下を確認します。

1. `npm run build` が成功すること。
2. `npm run dev -- --host 127.0.0.1 --port 4323` で対象ページを開けること。
3. 幅 `320px / 375px / 414px / 768px / 1440px` を確認すること。
4. 375px前後では、上から最後までスクロールして確認すること。
5. 横スクロール、画像の変形、文字の切れ、画像間の白線、重なり、CTAのはみ出しがないこと。
6. 高速スクロールしても、話題の変化が自然に分かること。
7. CTAをキーボードとタップで確認し、外部リンク、押下状態、縮小表示での矢印・枠の整合を確認すること。
8. CTAの前後に余計な空白を増やしていないこと。PCでもスマホの読み順が崩れていないこと。

## 7. 公開前・公開後の手順

### 公開前

1. ユーザーが「公開して」と明示的に承認したことを確認する。
2. `git status --short` で対象外の変更が混ざっていないか確認する。
3. `public/CNAME` とリモートURLが目的の公開先であることを確認する。
4. 本番ビルドとモバイル確認を終える。
5. 変更内容をコミットする。Codex作業ブランチは `codex/` を使う。

### 公開

このリポジトリは `main` への反映でGitHub Pagesが更新されます。明示承認後に限り、対象コミットを `main` に反映します。

### 公開後

1. `https://kubota.hakobu-family.com/対象スラッグ/` がHTTP 200で開くことを確認する。
2. CDNの古い応答を避けるため、必要なら一時的なクエリ文字列を付けて、更新済みHTML・画像を確認する。
3. 実際のスマホ幅で、変更箇所とCTAを再確認する。
4. ユーザーには、公開済みURLと確認した内容だけを簡潔に伝える。
